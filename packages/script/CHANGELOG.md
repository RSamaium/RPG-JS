# @rpgjs/script

## 5.1.0

### Minor Changes

- ac90692: Add `@rpgjs/script`, sandboxed scripts for RPGJS: a JavaScript subset run by its own interpreter (never as JavaScript), which listens to the signals of the game. The API of scripts follows the one of RPGJS (`$player.showText`, `showChoices`, `showNotification`, `changeMap`, `addItem`, `getItem`, `getVariable`…) and the mapping from hooks to signals is data that `provideScripts` takes more of (`bindings`). Scripts have a `$map` (events and zones made from plain data, events and players read, variables of the map, weather, lighting, sounds, animations and screen shake) with the names of `RpgMap`. Scripts also run in a gameplay room that is not a map (`$room`, `player.joinRoom`, shared properties in the state of the room). Scripts listen to the signals of the game (`player.joinMap`, `player.leaveMap`, `player.levelUp`, `player.dead`, `event.action`, `event.touch`) with a declared filter, and `provideScripts` from `@rpgjs/script/server` plugs them into the server of a game.
- ff15973: Scripts read the database of the game with `$data`: `$data.get(type, id)` gives a copy of a record of a collection (or `undefined`) and `$data.list(type)` copies of the records of a collection (1 000 at most). On a real game the records are the ones RPGJS keeps in the database of the room, with `_type` for their collection, as `@rpgjs/studio` loads them, so a script can read the collections a project adds (quests, for example). A simulation takes the records in `world.data`.
- 374516d: Scripts open the GUIs of the client: `$player.openGui(id, data?, { blockPlayerInput? })`, `$player.updateGui(id, data)` and `$player.closeGui(id, data?)`, named after `player.gui(id).open/update` and `player.removeGui` of RPGJS. A GUI of the game (`rpg-…`) is refused. The new signal `gui.action` carries what a component sends (`gui`, `event`, `data`). It comes from a new server hook, `player.onGuiInteraction(player, { guiId, name, data })`, called for every GUI interaction.
